# impl-flow — 方針立案 → サブエージェント実装 → 多角レビュー

メインセッション（上位モデル）は**実装コードを書かない**。方針・レビュー総括・差し戻し判断に徹し、手を動かすのはサブエージェント。

**適用範囲**: 複数ファイルにまたがる変更、またはロジックを含む変更。軽微な修正（typo・スタイル調整・設定1行など）はこのフローを省略してよい。

**プロジェクト規約が優先**: 作業リポジトリの CLAUDE.md に同種のフロー・worktree 運用・役割分担（例: 特定パッケージはユーザー本人が実装する等）が定義されていれば、**書かれている点はそちらに従い、書かれていない点はこのスキルに従う**。サブエージェントはこのスキルを読み込まないことがあるので、メインセッションが該当する手順の本文を指示に貼る。

**プロジェクトが差し込む場所**（このスキルは「何を満たせば済んだか」を決め、「どうやるか」はプロジェクトが持つ）:

| 差し込み口 | 置き場所 | 無いとき |
|---|---|---|
| 動作確認のやり方 | リポジトリの `.claude/skills/verify/SKILL.md` | その変更で一番安く実物に触れる方法を選び、完了報告で `verify` スキルにまとめることを提案する |
| 追加のレビュワー・観点 | CLAUDE.md の実装フローの節 | 手順4の既定のレビュワーだけ |
| 機械チェックの一覧 | CLAUDE.md（lint・typecheck・テストのコマンド） | 存在するものをすべて |

## 手順

### 1. 方針立案（メインセッション）

実装方針を立てる: 対象ファイル・変更の構造・使う API/型・エッジケース・テスト観点。不明点が実装を左右するならユーザーに確認してから進む。

方針に必ず入れるもの:

- **外部の相手の仕様**: 外部 SDK・Webhook・ストア・管理画面・ガイドラインに関わる変更では、相手の一次資料（公式ドキュメント・サンプル payload・ID の文字種や長さの制約・管理画面のテスト送信の形・ブランドガイドライン）を確かめ、方針に書く。自作の fixture だけで閉じない。
- **待ちの見え方**: LLM・外部 API・Webhook など本番で遅い経路を待つ UI は、遅いとき・失敗したときにどう見えるかを書く（モックやローカルは即応答して遅さを隠す）。
- **デザイン元との対応**: デザイン（Figma 等）に無い分岐・状態・近似を足す予定があれば、方針の段階でユーザーに確認する。

### 2. 実装（サブエージェント / model: opus）

Agent ツールで実装エージェントを起動する（`model: "opus"`）。渡すもの:

- 手順1の実装方針（そのまま全文）
- リポジトリの規約参照先（CLAUDE.md / AGENTS.md）と「規約に従うこと」
- ブランチ運用（下記「worktree 運用（herdr）」を指示に含める）
- 「実装完了後、lint / typecheck / テストなど存在する機械チェックをすべて実行し、通してから報告すること」

#### worktree 運用（herdr が既定）

- **作成**: `herdr worktree create --cwd <リポジトリルート> --branch <ブランチ名> --no-focus --json`。worktree は `~/.herdr/worktrees/<リポジトリ名>/<ブランチ名スラグ>` に作られる。結果 JSON の `workspace.workspace_id` と `worktree.path` を控える。**`--no-focus` 必須**（ユーザーの画面フォーカスを奪わない）
- **罠**: worktree は**そのとき checkout 中のブランチから分岐**する。作成直後に `git fetch origin <デフォルトブランチ>` → `git reset --hard origin/<デフォルトブランチ>` してから作業を始めること
- **フォールバック**: `herdr` コマンドが無い環境では、通常の feature ブランチ（または `git worktree`）で代替する

実装エージェントはレビュー通過後の PR 作成まで担うので、同じエージェントに SendMessage で追加指示できるよう ID を控える。

### 3. 機械チェック（レビューの前提条件）

動作確認・レビューに進む前に、lint・typecheck・テストが**すべて通っていること**を確認する（機械で拾える問題に LLM レビューを使わない）。落ちていれば手順2のエージェントに修正させる。

### 3b. 動作確認（実物で確かめる）

「コンパイルが通った」「テストが通った」で完了にしない。実装エージェントが、変更した振る舞いを**実物で動かして**確かめる。**やり方はリポジトリの `verify` スキル**（`.claude/skills/verify/SKILL.md`）に従う。無ければ、その変更で一番安く実物に触れる方法を選ぶ（ローカルサーバーへの curl・ブラウザ操作・CLI の実行・シミュレータなど）。

**満たすこと**（どのプロジェクトでも同じ）:

- **証拠を残す**: スクショ・ログ・リクエストとレスポンス。レビュワーに渡し、PR の「動作確認」節に載せる。
- **本番のデータを汚さない**: モック・ローカル・テスト環境を使う。
- **既存の E2E を追随させる**: 画面の文言・配置・遷移を変えたら、それを見ている E2E フローも同じ変更で直して回す。
- **UI を変えたら次も見る**（実行できる範囲で）: 触った画面のスクショ / ボタンの連打（押した後に同じ位置へ別のボタンが来ないか）/ 途中のステップでの強制終了と再起動 / 下端までスクロールした状態での操作 / 文字サイズ最大。
- **待ちがある変更は遅くして見る**: 外部待ちを本番並みに遅らせて（遅延プロキシ・モックの遅延設定）、待ちの間の見え方を確かめる。
- **手動 QA 項目を分ける**: 自動で確かめられない項目（実機だけの機能・体感・外部サービス）は控え、承認後に `/qa-request` で渡す。

動作確認で落ちたら、機械チェックと同じくレビューの前に直させる。2 サイクル目以降は、修正が触れた振る舞いだけ確かめ直す。

### 4. レビュー（並列サブエージェント）

成果物の diff・手順1の方針・手順3b の動作確認の結果を渡し、以下のレビュワーを**1つのメッセージで並列に**起動し、それぞれ独立に所見を出させる:

- **実装の擁護者** — 方針・仕様を満たしている根拠を挙げ、想定される批判に反論する
- **実装の批判者** — バグ・仕様違反・エッジケース・設計上の弱点を積極的に指摘する
- **セキュリティレビュワー** — 認証・入力検証・情報漏洩・依存関係などセキュリティ観点
- **コーディング規約レビュワー** — 命名/イディオム・CLAUDE.md / AGENTS.md のルール準拠（lint で機械判定できる範囲は手順3に任せる）
- **アーキテクトレビュワー**（変更が構成・依存方向・責務分割に影響する場合のみ）— 構造観点
- **プロジェクトが足すレビュワー**（CLAUDE.md に定義があれば）

批判者には次の観点を必ず含める: 時間軸（途中での強制終了・連打・遅延・二重発火）/ 外部の相手の仕様との食い違い / デザイン元との不一致や、デザイン元に無い分岐の追加。

### 5. 総括（メインセッション）

各レビュワーの所見（擁護と批判の対立点含む）を突き合わせ、**差し戻し**か**承認**を判断する:

- **差し戻し**: blocking な指摘（バグ・仕様違反・セキュリティ問題）が残っている → 修正指示を付けて手順2のエージェントへ戻す
- **承認**: blocking がゼロ。non-blocking な指摘（好みレベルの改善提案）は差し戻さず、**PR 説明に記載してユーザーの確認に委ねる**

**仕分けの基準**（レビュワーが気づいていたのに後回しにして不具合になる、を防ぐ）:

- 次は**既定で blocking**: ユーザーに誤った情報が表示される / タップ先がずれる・意図しない操作が起きる / デザイン元と一致しない、またはデザイン元に無い分岐・近似を足した（ユーザーの明示の承認があれば除く）。
- 「起こりうる」という予見の指摘は、**手順3b のやり方で再現を試してから**仕分ける。再現したら blocking。再現できない環境の話（実機だけ等）なら、手動 QA 項目に必ず載せる。
- **同じ種類の指摘が以前の PR でも出ていた**ら（PR 履歴・memory から分かる範囲で）、文章のルールを足すのではなく lint・テスト・共通部品にする案を、PR 説明のユーザー判断事項に入れる。

### 6. ループと上限

手順2〜5（3b を含む）で1サイクル、**上限5サイクル**。2サイクル目以降は**批判者＋前回指摘に関係するレビュワーのみの差分確認**でよい（フル再レビューしない）。5サイクルで承認に至らなければ打ち切り、争点と未解決事項をユーザーに報告して判断を仰ぐ。

## 承認後

実装エージェントに feature ブランチからの PR 作成を指示する。PR 説明には non-blocking 指摘の一覧と「動作確認」節（何を回したか・スクショは `gh pr edit --attach` で添付）を含める。

**QA が必要なら Slack でユーザーに依頼する**: 手順3b で自動では確かめられなかった項目（実機での見た目・操作感、外部サービスの画面、課金の実挙動など）が残る場合は、PR 作成後に **`/qa-request` スキルで Slack に QA 依頼を送る**（ユーザーへのメンション付き）。PR 本文にも同じチェックリストを「実機 QA 依頼」節として載せる。プロジェクトの運用で QA をまとめて後回しにすると決まっている場合（例: スタック PR を全部マージしてから 1 回で QA）は、その時点では送らず、まとめるタイミングで送る。QA が不要な変更（CI・ドキュメント・テストで挙動が確定するもの）では送らない。

**ツアーを裏で用意する（diff-tour）**: レビュワーの承認とは別に、マージ前にユーザー自身が変更を理解するための段階。PR 作成後、worktree の workspace に新しいタブを開いて `tour` を走らせておく（生成に 2〜5 分かかるのでユーザーが開く前に済ませる）。手順の詳細は単体スキル `diff-tour` にある（要点は以下）:

```sh
pane=$(herdr tab create --workspace <workspace_id> --cwd <worktree.path> --label tour --no-focus --json | jq -r '.result.root_pane.pane_id')
herdr pane run "$pane" "tour <ブランチ名>"
```

- **`--no-focus` 必須**。`tour` は対話型 TUI なので、起動後は触らない（中身を読むのはユーザー）。
- QA 依頼・完了報告に「herdr の `tour` タブでツアーを用意した」と一言添える。
- 対象は手順1の適用範囲と同じく、ロジックを含む変更だけ。設定・ドキュメントだけの変更では作らない（1 回あたり API 換算で $1〜1.5 かかる）。
- `herdr` または `tour` コマンドが無い環境では省略し、「`tour <ブランチ名>` で読める」と報告に書くだけにする。

worktree の後始末（マージ後）: `herdr worktree remove --workspace <workspace_id>`。**ブランチは残るので `git branch -d <ブランチ名>` で別途削除する。**
