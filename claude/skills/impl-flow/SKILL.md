# impl-flow — 方針立案 → サブエージェント実装 → 多角レビュー

メインセッション（上位モデル）は**実装コードを書かない**。方針・レビュー総括・差し戻し判断に徹し、手を動かすのはサブエージェント。

**適用範囲**: 複数ファイルにまたがる変更、またはロジックを含む変更。軽微な修正（typo・スタイル調整・設定1行など）はこのフローを省略してよい。

**プロジェクト規約が優先**: 作業リポジトリの CLAUDE.md に同種のフロー・worktree 運用・役割分担（例: 特定パッケージはユーザー本人が実装する等）が定義されていれば、そちらの定義に従う。このスキルは既定値。

## 手順

### 1. 方針立案（メインセッション）

実装方針を立てる: 対象ファイル・変更の構造・使う API/型・エッジケース・テスト観点。不明点が実装を左右するならユーザーに確認してから進む。

### 2. 実装（サブエージェント / model: opus）

Agent ツールで実装エージェントを起動する（`model: "opus"`）。渡すもの:

- 手順1の実装方針（そのまま全文）
- リポジトリの規約参照先（CLAUDE.md / AGENTS.md）と「規約に従うこと」
- ブランチ運用（下記「worktree 運用（herdr）」を指示に含める）
- 「実装完了後、lint / typecheck / テストなど存在する機械チェックをすべて実行し、通してから報告すること」

#### worktree 運用（herdr が既定）

- **作成**: `herdr worktree create --cwd <リポジトリルート> --branch <ブランチ名> --no-focus --json`。worktree は `~/.herdr/worktrees/<リポジトリ名>/<ブランチ名スラグ>` に作られる。結果 JSON の `workspace.workspace_id` と `worktree.path` を控える。**`--no-focus` 必須**（ユーザーの画面フォーカスを奪わない）
- **罠**: worktree は**そのとき checkout 中のブランチから分岐**する。作成直後に `git fetch origin <デフォルトブランチ>` → `git reset --hard origin/<デフォルトブランチ>` してから作業を始めること
- **フォールバック**: `herdr` コマンドが無い環境では、通常の feature ブランチ（または `git worktree`）で代替する

実装エージェントはレビュー通過後の PR 作成まで担うので、同じエージェントに SendMessage で追加指示できるよう ID を控える。

### 3. 機械チェック（レビューの前提条件）

レビューに進む前に、lint・typecheck・テストが**すべて通っていること**を確認する（機械で拾える問題に LLM レビューを使わない）。落ちていれば手順2のエージェントに修正させる。

### 4. レビュー（並列サブエージェント）

成果物の diff と手順1の方針を渡し、以下のレビュワーを**1つのメッセージで並列に**起動し、それぞれ独立に所見を出させる:

- **実装の擁護者** — 方針・仕様を満たしている根拠を挙げ、想定される批判に反論する
- **実装の批判者** — バグ・仕様違反・エッジケース・設計上の弱点を積極的に指摘する
- **セキュリティレビュワー** — 認証・入力検証・情報漏洩・依存関係などセキュリティ観点
- **コーディング規約レビュワー** — 命名/イディオム・CLAUDE.md / AGENTS.md のルール準拠（lint で機械判定できる範囲は手順3に任せる）
- **アーキテクトレビュワー**（変更が構成・依存方向・責務分割に影響する場合のみ）— 構造観点

### 5. 総括（メインセッション）

各レビュワーの所見（擁護と批判の対立点含む）を突き合わせ、**差し戻し**か**承認**を判断する:

- **差し戻し**: blocking な指摘（バグ・仕様違反・セキュリティ問題）が残っている → 修正指示を付けて手順2のエージェントへ戻す
- **承認**: blocking がゼロ。non-blocking な指摘（好みレベルの改善提案）は差し戻さず、**PR 説明に記載してユーザーの確認に委ねる**

### 6. ループと上限

手順2〜5で1サイクル、**上限5サイクル**。2サイクル目以降は**批判者＋前回指摘に関係するレビュワーのみの差分確認**でよい（フル再レビューしない）。5サイクルで承認に至らなければ打ち切り、争点と未解決事項をユーザーに報告して判断を仰ぐ。

## 承認後

実装エージェントに feature ブランチからの PR 作成を指示する。PR 説明には non-blocking 指摘の一覧を含める。

**QA が必要なら Slack でユーザーに依頼する**: 実機での見た目・操作感、外部サービスの画面、課金の実挙動など、機械チェックとレビューでは確かめられない確認が残る場合は、PR 作成後に **`/qa-request` スキルで Slack に QA 依頼を送る**（ユーザーへのメンション付き）。PR 本文にも同じチェックリストを「実機 QA 依頼」節として載せる。プロジェクトの運用で QA をまとめて後回しにすると決まっている場合（例: スタック PR を全部マージしてから 1 回で QA）は、その時点では送らず、まとめるタイミングで送る。QA が不要な変更（CI・ドキュメント・テストで挙動が確定するもの）では送らない。

worktree の後始末（マージ後）: `herdr worktree remove --workspace <workspace_id>`。**ブランチは残るので `git branch -d <ブランチ名>` で別途削除する。**
