# qa-request — QA 依頼を組み立てて Slack に投げる

**Slack で bao さん（メンバー ID `U0ARPR7SUUD`）にメンションして依頼する**のが既定。impl-flow の承認後に QA が必要なときもこのスキルを使う。

Claude には実機やユーザーのアカウントで確認できないこと（実機の見た目・操作感・ストア/外部サービスの画面・課金の実挙動など）を、**ユーザーがそのまま手を動かせる形**で依頼する。

## 1. 依頼の中身を集める

- **出どころ**: 対象 PR 本文の「実機 QA」「動作確認」「QA 依頼」節（`gh pr view <n> --json body`）、実装サブエージェントの報告、Issue のチェックリスト。複数 PR をまとめるときは全部集める。
- **複数 PR をまとめて 1 回で QA する**（スタック PR を順にマージしてから最終形で確認する運用）なら:
  - 重複する項目は 1 つにする。
  - 後の PR が上書きした画面・挙動は、最終形の説明に合わせて書き直す（古い PR の手順をそのまま載せない）。
  - 画面の遷移順（起動 → 登録 → メイン → 詳細 → 設定…）に並べ替える。
  - 各項目の末尾に元の PR 番号を `（#123）` で付ける。不具合報告を受けたときの切り分けに使う。
- **確認環境を明記する**: 接続先（本番 API / ローカル）、アプリの起動方法（Expo Go / dev client / シミュレータ等）、必要な事前準備（環境変数、テスト用アカウント、データの投入）。ビルドの作り直しが要る項目は分けて書く。
- **ユーザーにしか分からないことは推測で埋めない**（テスト端末の OS バージョン等）。

## 2. 書式

Slack の mrkdwn で書く（`*太字*`、`<URL|表示名>` のリンク、`•` 箇条書き）。チャットにも同じ内容を Markdown で出す。

```
<@U0ARPR7SUUD> :test_tube: *QA 依頼: <対象の短い説明>*
環境: <接続先> / <起動方法>
準備: <事前にやること>

*<画面・機能のまとまり 1>*
• <操作> → <期待する結果>（#123）
• ...

*<まとまり 2>*
• ...

終わったら: <どう報告してほしいか（例: 問題の項目番号とスクショを返信）>
PR: <https://github.com/.../pull/123|#123 タイトル>, ...
```

- **先頭で必ずユーザーをメンションする**: `<@U0ARPR7SUUD>`（bao さんの Slack メンバー ID）。Incoming Webhook でも `<@ID>` 形式ならメンションとして通知が飛ぶ（表示名の `@bao` 等は通知されない）。別のユーザーに依頼するときは、その人のメンバー ID に置き換える。
- 1 項目 = 1 操作 + 期待結果。「〜が正しく動く」のような曖昧な書き方をしない。
- 項目が多いときは、優先度の高いもの（リリースを止める不具合が出うるもの）を先に並べる。

## 3. 送る

1. 環境変数 `SLACK_QA_WEBHOOK_URL` を確認する。**値は表示しない**（`test -n "$SLACK_QA_WEBHOOK_URL"` で有無だけ見る）。プロジェクトでは gitignore 済みの `mise.local.toml` の `[env]` に置く運用なので、`mise exec --` 経由で読む。
2. JSON は必ず `jq -n --arg text "$MSG" '{text:$text}'` で組み立てる（文字列連結で JSON を作らない。PR タイトル等に `"` や改行が入っても壊れないように）。本文中の `&` `<` `>` は、リンク記法以外の場所では `&amp;` `&lt;` `&gt;` にエスケープする。
3. `curl -sS --max-time 10 -o /dev/null -w '%{http_code}' -X POST -H 'Content-type: application/json' --data "$JSON" "$SLACK_QA_WEBHOOK_URL"` で投稿し、200 を確認する。
4. **Webhook が無い・失敗したら**、チャットに同じ内容を書いて「Slack には届いていない」と一言添える。Webhook の URL はチャットやログに出さない。
5. 送ったら、チャットには短く「#<チャンネル> に QA 依頼を送った」＋ 要点（項目数・所要時間の目安・特に見てほしい所）だけ書く。全文の重複貼りはしない（Slack が失敗したときを除く）。

## 4. 結果を受けたら

- 問題の報告は項目の PR 番号で原因の PR を当たりを付け、修正は通常の実装フロー（impl-flow 等）で行う。
- 全項目 OK なら、該当 PR / Issue のチェックリストを更新し、プロジェクトのメモリや引き継ぎ資料の「QA 待ち」を消す。

## 初回セットアップ（Webhook が無いとき）

ユーザーに依頼する: Slack の https://api.slack.com/apps → Create New App → From scratch → Incoming Webhooks を On → Add New Webhook to Workspace でチャンネルを選ぶ → 発行された URL を `mise.local.toml`（gitignore 済み）の `[env]` に `SLACK_QA_WEBHOOK_URL = "..."` で追加。URL はチャットに貼らないよう伝える。追加されたらテスト投稿で到達を確認する。
